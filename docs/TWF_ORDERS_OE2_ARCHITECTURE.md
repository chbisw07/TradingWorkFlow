# TWF Orders OE-2 — Manual Order Intake

Version 1.2 — 14 October 2026. Status: **OE2-F1 and OE2-R1 remediated; independent acceptance pending**. OE-1 remains **accepted / frozen**. This document describes the OE-2 application layer; [the OE-1 domain architecture](TWF_Order_Domain_and_Lifecycle_Architecture.md) remains normative for identity, ownership, lifecycle, and persistence.

## Purpose and boundary

Top-level **Orders** now shows owner-scoped TWF Orders and provides **+ New Order**. It reuses the existing Broker New Order component's Select Instrument → Ticket → Preview → Result stages. The new `TWF_ORDER` destination calls the OE-2 API; the default `BROKER_DIRECT` destination remains operational for Brokers, Watchlists, and Scanners during migration. OE-2 creates a manual TWF Order, validates it, and stops at **READY**. There is no Queue table, API, entry, worker, `READY → QUEUED` transition, or broker execution call in this path.

## Trusted resolution and creation

`POST /api/v1/twf-orders/preview` accepts only the selected broker account and instrument reference/token plus typed user intent (side, quantity, MARKET/LIMIT, price, product, validity, notes). It reads the authenticated owner's connected account and server-owned structured broker instrument catalog. Exact reference and native token must identify one executable catalog row. The application bridge derives Equity/FUTSTK/FUTIDX/OPTSTK/OPTIDX identity from structured catalog fields, option resolution, known canonical index classification, and a corresponding NSE equity listing where needed. Ambiguous or incomplete underlying, expiry, strike, lot, or tick data is rejected. Exchange expiry is parsed as an ISO **date**, without a UTC conversion. Provider tokens remain at the resolution boundary and are not persisted in the OE-1 order instrument.

Preview stores a five-minute, server-owned envelope in `manual_order_previews` and returns its opaque `preview_id` with the projected canonical instrument, normalized terms, and expiry. The envelope binds authenticated owner and session, broker account, a digest of the exact catalog selection, the entire provider-neutral instrument projection (including asset class, exchange, underlying, expiry, strike/right, lot/tick), normalized order terms, notes, and MANUAL source. It stores no native token, credential, or access secret. Preview issuance opportunistically removes records that expired more than one day ago; no scheduler or Queue worker is involved. Preview states that no broker order will be submitted. At final Create, the server reloads the envelope, checks owner/session/account and expiry, re-resolves current server catalog truth, and compares the fresh canonical projection, all terms, notes, and source to the server snapshot. A different valid contract or any material term change returns `PREVIEW_MISMATCH`; expiry, missing/cross-owner, and prior use have distinct typed errors. Browser preview data is never promoted to canonical authority. The request contract rejects owner, source, actor, lifecycle state, version, and caller-provided canonical contract facts. Source is **MANUAL** and actor is the authenticated user through OE-1 `OrderContext.from_authenticated_session`. The bridge binds the resolved identity to OE-1's trusted canonical authority, calls `CreateOrder`, then `ValidateForReadiness`, then transitions `DRAFT → READY` only when validation passes. Expected readiness failures remain inspectable DRAFT orders with structured validation violations and a persisted validation event. Unexpected resolution/persistence failures do not claim READY.

This uses the existing OE-1 order and event tables. There is no second order store. The user can list the latest 50 owner-scoped orders, view a persisted order, and inspect its real audit events through `GET /api/v1/twf-orders`, `GET /api/v1/twf-orders/{id}`, and `GET /api/v1/twf-orders/{id}/history`. Other owners' IDs and history are unavailable. The Orders UI refreshes after creation and loads details from persisted server state. The Next.js proxy forwards only the OE-2 read, preview, and create routes.

## Execution and compatibility

TWF Order creation never invokes broker place, modify, or cancel. The broker catalog and capability endpoints are used for instrument selection/resolution; they are not order submission. Broker + New Order and existing Watchlist/Scanner Buy/Sell continue using the default Broker V2 flow. This temporary direct Broker path remains until a later, explicitly reviewed migration. The governing target rule remains: **No TWF subsystem may initiate a broker order except through the governed TWF execution path.** OE-2 prepares that future path but does not implement it.

Create conditionally locks the open Preview row inside an OE-2 owned database transaction. Frozen OE-1 `CreateOrder`, readiness validation, and `DRAFT → READY` use connection-bound sessions whose transactions join that outer transaction as savepoints. The Preview's consumed timestamp, resulting `twf_order_id`, and validation result are written together before the outer commit. An error at any point rolls back the claim, order, events, transition, and link, leaving an unexpired Preview reusable. The Preview table enforces a linked-order foreign key, a unique order link, and an all-or-none consumed/order/validation constraint.

Concurrent Create requests for the same valid Preview converge on exactly one durable Order. Once committed, the same owner and authenticated session can replay the same Preview and receive the existing order and original validation as a successful response; no second order is created. A changed selection or terms still returns `PREVIEW_MISMATCH`, and an expired unconsumed Preview cannot create an order. A Preview valid at its conditional claim may finish after its expiry because the claim timestamp governs validity. Known SQLite busy/locked conflicts retry the entire operation from fresh Preview and catalog truth, with six bounded attempts and short deterministic backoff; other errors are not retried. The UI can therefore display the existing order after a concurrent replay or lost response. This is Preview-ID idempotency only: two different Previews for the same trade may still create two orders. Global create idempotency and automated webhook/Queue idempotency remain deferred.

## Acceptance model

Backend integration tests use an authenticated API, actual migrations, and an in-process synthetic broker catalog/transport. They cover Equity, index and stock Futures, index and stock Options, exact exchange dates and lot/tick/strike/CE/PE, list/detail/history, owner isolation, spoofed authority fields, invalid readiness as DRAFT, CSRF/origin enforcement, and zero broker submissions. OE-1 and existing Broker tests are regression gates. Frontend tests exercise the same shared ticket in both destinations, including preview and double-click protection. Browser validation should additionally cover the 390/768/1024/1440/1920/2560 widths and a connected account; it must not be replaced by unit-test assertions.
